# Command instances have one configured executor owner

A command instance belongs to one configured Executor composition root; multiple fake/create adapters from that root are allowed, but another configured Executor must use fresh command instances. We chose rejecting cross-executor reuse over supporting it through invocation-scoped registry/help metadata, preventing another composition root from rebinding mutable framework metadata while retaining repeated adapter creation. This restriction does not bind immutable input declaration handles to one executor or promise thread safety. Complete composition validation precedes atomic ownership claiming at Executor construction; failed construction claims no commands and cannot rebind an existing owner's metadata. One command object occupies one canonical path (aliases do not create placements), and overlapping invocations across the owner's adapters raise StateError rather than queue or return a CLI failure result. Sequential reuse is supported, scalar hook context is retained across all adapters from that owner, and guard release must survive thrown failures even though hook cleanup retains its Exception-only boundary.
